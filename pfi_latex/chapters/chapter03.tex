\section{Historias de Usuario}

\begin{itemize}
	\item HU01 -- Como vendedor, quiero visualizar un ranking de productos en tendencia por categoría para decidir qué publicar.
	\item HU02 -- Como vendedor, quiero recibir una alerta cuando un producto que sigo empiece a crecer en tendencia, sin tener que entrar a revisar el dashboard.
	\item HU03 -- Como comprador, quiero ver el histórico de precio de un producto antes de comprarlo.
	\item HU04 -- Como usuario, quiero filtrar productos por categoría, rango de fecha y precio.
	\item HU05 -- Como administrador, quiero configurar la frecuencia de captura de datos desde la API de Mercado Libre (implementada mediante tareas programadas del sistema operativo: tres corridas diarias parametrizables).
	\item HU06 -- Como cliente, quiero crear una cuenta para acceder a las funciones del nivel pago del modelo freemium (historial completo, exportación y alertas).
	\item HU07 -- Como cliente, quiero seguir un producto puntual desde el ranking, para que el sistema me avise si empieza a crecer en vez de tener que revisarlo yo.
\end{itemize}

\section{Requerimientos Funcionales}

\begin{enumerate}
	\item RF01 -- El sistema debe capturar periódicamente datos de productos desde la API oficial de Mercado Libre.
	\item RF02 -- El sistema debe calcular un score de tendencia por producto en base a variables temporales.
	\item RF03 -- El sistema debe permitir filtrar y ordenar productos por categoría, score, variación de precio, rango de precio y rango de fecha.
	\item RF04 -- El sistema debe exponer los resultados mediante una API REST (Next.js API Routes).
	\item RF05 -- El sistema debe mostrar, en el dashboard, gráficos de evolución temporal por producto y categoría.
	\item RF06 -- El sistema debe permitir exportar el listado de productos en tendencia (CSV).
	\item RF07 -- El sistema debe exponer, para cada producto activo, el índice de prioridad calculado por el modelo de Machine Learning supervisado (Sección~\ref{chapter-ml}), que ordena los productos según su chance de que el score siga creciendo.
	\item RF08 -- El sistema debe permitir a un usuario crear una cuenta y autenticarse, para diferenciar el nivel gratuito del nivel pago del modelo freemium (Sección~\ref{sec:modelo-negocio}).
	\item RF09 -- El sistema debe permitir a un cliente autenticado seguir un producto puntual y generar una alerta cuando su score cruce el umbral de crecimiento (HU07).
\end{enumerate}

\section{Requerimientos No Funcionales}

\begin{enumerate}
	\item RNF01 -- El sistema debe respetar los límites de rate-limit de la API oficial de Mercado Libre durante la captura de datos.
	\item RNF02 -- El sistema debe responder las consultas del dashboard en menos de 3 segundos sobre el dataset histórico. El modelo de datos incluye índices en PostgreSQL (productId, timestamp, categoryId) diseñados para sostener ese tiempo de respuesta a medida que el histórico escala.
	\item RNF03 -- El sistema debe poder desplegarse en plataformas cloud con escalado gestionado. Actualmente se despliega en Render con build reproducible (generación de Prisma Client en postinstall).
	\item RNF04 -- El sistema debe persistir los datos históricos con respaldo (backup) periódico.
	\item RNF05 -- El sistema debe gestionar las credenciales y tokens de acceso (OAuth2 de Mercado Libre) exclusivamente del lado servidor, sin exponerlos nunca al cliente, con renovación automática de tokens.
	\item RNF06 -- El sistema debe exigir autenticación para acceder al panel administrativo (\texttt{/admin}), dado que expone información operativa interna (logs de minería, estado de endpoints).
	\item RNF07 -- El sistema debe almacenar las contraseñas de los usuarios con hash seguro (nunca en texto plano ni reversible).
\end{enumerate}

\section{Diseño del sistema}\label{sec:diseno-sistema}

Esta sección reúne las decisiones de diseño que definen qué mide el sistema: las decisiones técnicas generales, la identidad del producto, la fórmula del score de tendencia y el diseño del modelo supervisado. Se presentan después de los requerimientos porque responden a ellos (RF02 y RF07) y antes de la metodología, que describe cómo se implementaron.

\subsection{Decisiones técnicas generales}

Las decisiones técnicas adoptadas dentro del proyecto responden principalmente a la necesidad de garantizar escalabilidad, automatización, persistencia histórica y capacidad analítica. El detalle del stack tecnológico elegido, su evolución durante la implementación y la arquitectura general del sistema se desarrollan en la Sección~\ref{sec:metodologia} (Arquitectura y tecnologías utilizadas).

Para eso, se plantea una arquitectura basada en APIs REST oficiales, permitiendo acceder a información estructurada y confiable proveniente del marketplace. Asimismo, la construcción de datasets históricos resulta fundamental para realizar análisis temporales y detectar patrones de crecimiento sostenido.

La factibilidad de construir ese histórico de forma propia, sin depender de un dataset externo preexistente, se apoya en tres condiciones concretas: la API oficial de Mercado Libre expone de forma pública y gratuita los campos necesarios (publicaciones, precios, categorías y atributos de producto); el volumen de solicitudes requerido por una captura periódica se mantiene dentro de los límites de rate-limit publicados por la plataforma (RNF01); y el costo de almacenamiento de ese histórico en una base de datos relacional gestionada es marginal frente al valor analítico que aporta con el tiempo (Sección~\ref{sec:viabilidad-economica}). El detalle del proceso de captura, su cadencia y el tratamiento de los datos se desarrolla en la Sección~\ref{sec:gestion-datasets}.

Por otro lado, la incorporación de técnicas de minería de datos permite extraer información relevante a partir de grandes volúmenes de datos, mientras que el uso de modelos supervisados posibilita analizar comportamientos emergentes y diferenciar tendencias reales de variaciones temporales aisladas.

La implementación de dashboards analíticos y mecanismos de monitoreo contribuye a mejorar la visualización de métricas, el seguimiento de tendencias y la disponibilidad operativa de los servicios utilizados.

\subsection{Identidad del producto}\label{sec:identidad-producto}

Una misma referencia comercial (por ejemplo, un modelo puntual de auricular o de organizador de placard) suele estar publicada en Mercado Libre por decenas de vendedores distintos, cada uno con su propio precio, stock y reputación. Conviene aclarar explícitamente a cuál de esas instancias se refiere el sistema cuando calcula un score de tendencia, dado que la ambigüedad afectaría directamente la interpretación de los resultados.

El score de tendencia está pensado para responder la pregunta del vendedor (``¿este producto, dentro de mi categoría, está ganando o perdiendo tracción?''), no para declarar cuál es ``el'' ganador entre publicaciones equivalentes de la competencia. El componente de ranking de la fórmula (Sección~\ref{sec:score-formal}) ya captura parte de esa dimensión competitiva, al comparar la posición del producto contra los demás de su misma categoría.

Con esa aclaración hecha, el sistema resuelve la identidad de un producto contra el identificador de catálogo de Mercado Libre (\texttt{catalogProductId}, expuesto por \texttt{/products/search} y \texttt{/products/\{id\}/items}), no contra la publicación puntual de un vendedor: mientras el catálogo esté disponible para la categoría, esa es la clave estable de cada fila de producto, y \texttt{mlId} pasa a ser solamente un dato informativo: cuál es la publicación más barata vigente en la última corrida de minería, que puede cambiar de vendedor sin que el sistema lo trate como ``otro'' producto. Antes de este ajuste, un cambio de vendedor más barato de una corrida a otra cortaba el histórico de apariciones y scores del producto, un riesgo real para la continuidad del análisis temporal de cada producto. Los productos capturados antes de este cambio (sin \texttt{catalogProductId} vinculado todavía) se enlazan automáticamente la primera vez que la minería los vuelve a encontrar, en lugar de duplicarse. Las tres situaciones (alta nueva, cambio de vendedor más barato y enlace de una fila previa) se probaron contra la base de producción antes de desplegar el cambio.

Con la identidad del producto ya resuelta contra el catálogo, quedaba una limitación relacionada: el score seguía calculándose sobre la señal de una sola publicación (la más barata) en cada momento, y no sobre una agregación simultánea de las apariciones de todos los vendedores que compiten por ese mismo producto. Esto también se resolvió: el componente de estabilidad de precio pasó a calcularse sobre el promedio entre vendedores activos, y la cantidad de vendedores se incorporó como un quinto componente ponderado de la fórmula (saturación), según se detalla en la Sección~\ref{sec:score-formal}.

\subsection{Definición formal del score de tendencia (RF02)}\label{sec:score-formal}

El indicador compuesto de la Tabla~\ref{tab:metricas} es, en la implementación actual, el score de tendencia: un valor entre 0 y 100 calculado para cada producto sobre una ventana de análisis de 7 días, que combina cinco componentes normalizados entre 0 y 1:

\begin{equation}
	\text{score} = 100 \times (0{,}30 \cdot f + 0{,}21 \cdot p + 0{,}17 \cdot r + 0{,}17 \cdot e + 0{,}15 \cdot s)
	\label{eq:score}
\end{equation}

donde:

\begin{itemize}
	\item \textbf{Frecuencia ($f$, peso 30\,\%)}: apariciones del producto dentro de la ventana, normalizadas contra el máximo de apariciones de cualquier producto en la misma corrida, calculado solo con la ventana de esa corrida y guardado junto con el score ($f = \text{apariciones}_{\text{producto}} / \text{apariciones}_{\text{máx}}$). Es relativa al resto del dataset, no un conteo absoluto.
	\item \textbf{Permanencia ($p$, peso 21\,\%)}: proporción de días distintos, dentro de la ventana, en los que el producto tuvo al menos una aparición ($p = \text{días con presencia} / 7$, acotado a 1). Diferencia una presencia sostenida de una aparición aislada.
	\item \textbf{Ranking ($r$, peso 17\,\%)}: posición promedio del producto dentro del catálogo de su categoría (1 a 8, ya que la minería captura 8 productos por categoría), invertida y normalizada: $r = \max(0,\, (9 - \text{posición promedio}) / 8)$. Una posición promedio 1 (la mejor) da $r=1$; una posición 8 da $r=0$.
	\item \textbf{Estabilidad de precio ($e$, peso 17\,\%)}: $e = \max(0,\, 1 - \min(1, |\Delta\%\text{precio}|))$, comparando el primer y el último precio registrado dentro de la ventana. Un precio estable da $e$ cercano a 1; una variación brusca (oferta relámpago, error de carga) lo acerca a 0. Si el producto solo tiene un registro de precio en la ventana, se usa un valor neutro $e = 0{,}5$ por falta de información suficiente. Desde el 23/09/2026, el precio que alimenta este componente es el \textbf{promedio entre todos los vendedores activos} detectados en cada aparición (hasta 5, vía \texttt{/products/\{id\}/items}), no el del vendedor más barato del momento; así la estabilidad no se ve afectada por un simple cambio de quién ofrece el precio más bajo de una corrida de minería a otra.
	\item \textbf{Saturación ($s$, peso 15\,\%)}: mide si el producto todavía tiene pocos vendedores compitiendo por él o si el mercado ya se consolidó. $s = \max(0,\, \min(1,\, 1 - (\overline{v} - 1)/4))$, donde $\overline{v}$ es la cantidad promedio de vendedores activos detectados en la ventana (\texttt{avgSellerCount}, de 1 a 5 según el límite de \texttt{/products/\{id\}/items}). Un producto con 1 solo vendedor activo da $s=1$ (todavía sin competencia real: la oportunidad temprana que describieron los vendedores entrevistados, Anexos~\ref{anexo:entrevista1} a~\ref{anexo:entrevista3}); con 5 vendedores da $s=0$ (mercado ya saturado). Para productos capturados antes del 24/09/2026, que todavía no tienen \texttt{avgSellerCount} registrado, se usa un valor neutro $s=0{,}5$, mismo criterio que ya se aplicaba a $e$ con un solo registro de precio.
\end{itemize}

Este quinto componente, incorporado el 24/09/2026, resuelve una limitación reconocida de la fórmula: la cantidad de vendedores pasó de ser un dato persistido solo a título informativo a ser un componente ponderado de la fórmula. Los cuatro pesos anteriores se reescalaron proporcionalmente (multiplicados por 0,85) para liberar el 15\,\% que ahora ocupa $s$, sin alterar su orden relativo de importancia.

Un producto se marca como ``en crecimiento'' (HU02, alerta) cuando su score sube 5 puntos o más respecto del cálculo anterior sobre el mismo producto.

\paragraph*{Ejemplo trabajado con datos reales del sistema}

A modo de ejemplo, el sistema calculó lo siguiente para un aro de luz LED profesional (categoría Celulares) el día 10 de agosto de 2026, con 21 apariciones registradas en la ventana de 7 días, bajo la metodología de precio de un solo vendedor, vigente hasta el 22/09/2026 (ver aclaración más abajo):

\begin{itemize}
	\item $f = 0{,}500$ (apariciones normalizadas contra el máximo de la corrida)
	\item $p = 1{,}000$ (presente los 7 días de la ventana)
	\item $r = 0{,}482$ (posición promedio $\approx 5{,}1$ de 8 en su categoría)
	\item $e = 1{,}000$ (precio sin variación en la ventana)
\end{itemize}

\[
	\text{score} = 100 \times (0{,}35 \cdot 0{,}500 + 0{,}25 \cdot 1{,}000 + 0{,}20 \cdot 0{,}482 + 0{,}20 \cdot 1{,}000) = 72{,}1
\]

Como contraste, otro producto de la misma categoría con una sola aparición en toda la ventana obtuvo $f=0{,}024$, $p=0{,}143$, $r=0{,}125$ y $e=0{,}5$ (neutro, por tener un solo registro de precio), resultando en un score de apenas $16{,}9$. Esto refleja correctamente que se trata de una aparición aislada y no de una tendencia sostenida.

\paragraph*{Agregación entre vendedores (actualizado 23/09/2026)}

El ejemplo anterior calculaba $e$ sobre el precio del vendedor más barato en cada corrida de minería, algo coherente con que, en ese momento, la identidad del producto todavía no estaba anclada al catálogo de Mercado Libre (Sección~\ref{sec:identidad-producto}). Una vez resuelta esa identidad, se corrigió también la estabilidad de precio para que se calcule sobre el promedio entre todos los vendedores activos, no sobre uno solo. Un caso real, verificado contra producción el mismo día del cambio: el producto de catálogo \texttt{MLA20659045} (Samsung Galaxy A04e, categoría Celulares) tenía 2 vendedores activos, con precios de \$180.000 y \$230.000: precio más barato \$180.000 (lo que se le sigue mostrando al comprador), precio promedio \$205.000 (lo que a partir de ahora alimenta $e$). Su score recalculado con este componente ya agregado dio $78{,}5$, con \texttt{avgSellerCount = 2} persistido junto al resto del desglose.

Como los aproximadamente 5800 registros de \texttt{PriceHistory} anteriores a este cambio fueron capturados con la metodología de un solo vendedor, los dos ejemplos trabajados arriba ($72{,}1$ y $16{,}9$) siguen siendo datos reales y válidos para la fecha en que se calcularon, pero no son directamente comparables con scores calculados después del 23/09/2026. El modelo de ML vigente (Sección~\ref{chapter-ml}) se entrenó el 09/10/2026 excluyendo los pares de scores que cruzan este cambio y la incorporación de la saturación descripta a continuación, porque su diferencia mide el cambio de fórmula y no el mercado (Sección~\ref{sec:variable-objetivo}).

\paragraph*{Incorporación de la saturación como componente ponderado (actualizado 24/09/2026)}

Hasta este cambio, \texttt{avgSellerCount} se calculaba y persistía junto al resto del desglose, pero solo a título informativo: no pesaba en la fórmula. Se incorporó como quinto componente ($s$, peso 15\,\%, ver definición formal más arriba) para que la cantidad de vendedores compitiendo por un mismo producto de catálogo influya directamente en el score, no solo se muestre como dato de contexto.

Mismo producto de catálogo del ejemplo anterior (\texttt{MLA20659045}, Samsung Galaxy A04e), recalculado en producción el mismo día del cambio, ahora con 23 apariciones en la ventana y 2 vendedores activos en promedio:

\begin{itemize}
	\item $f = 0{,}697$; $p = 1{,}000$; $r = 0{,}761$; $e = 0{,}861$
	\item $s = 0{,}750$ (2 vendedores activos: $s = 1 - (2-1)/4$)
\end{itemize}

\[
	\text{score} = 100 \times (0{,}30 \cdot 0{,}697 + 0{,}21 \cdot 1{,}000 + 0{,}17 \cdot 0{,}761 + 0{,}17 \cdot 0{,}861 + 0{,}15 \cdot 0{,}750) = 80{,}7
\]

Como con el cambio anterior, los scores calculados con la fórmula de cuatro componentes (incluido el $78{,}5$ del ejemplo previo) siguen siendo datos reales y válidos para la fecha en que se calcularon (cada registro de \texttt{TrendScore} persiste los pesos vigentes al momento de su cálculo, campo \texttt{weights} dentro de \texttt{components}), pero no son directamente comparables con scores calculados después del 24/09/2026.

El sistema persiste el desglose completo de los componentes junto con cada score calculado (no solo el número final), precisamente para que el resultado pueda auditarse y no funcione como una caja negra. Esto responde de manera directa al hallazgo de la Entrevista 2 (Sección~\ref{chapter06}), donde el entrevistado señaló que un score sin desglose no le genera confianza.

\subsection{Diseño del modelo supervisado}

En una primera etapa, el proyecto priorizó métricas descriptivas y reglas de análisis temporal, dejando sentado el diseño metodológico del modelo supervisado para aplicarlo cuando el histórico alcanzara un volumen mínimo razonable. Esta decisión es consistente con trabajos como el de \textcite{ElalemMaierSeifert2023}, donde se analiza la predicción de productos nuevos con ciclos de vida cortos y disponibilidad limitada de datos históricos. El modelo ya se entrenó y se evaluó: el diseño experimental completo, los controles contra la fuga de información y los resultados se presentan en la Sección~\ref{chapter-ml}.

El diseño se definió antes de tener volumen suficiente para entrenar, de modo que la construcción del histórico fuera compatible desde el principio con esta etapa. En síntesis:

\begin{itemize}
	\item \textbf{Variable objetivo}: clasificación binaria por producto, derivada de los propios datos históricos: 1 si el score sube al menos 5 puntos entre una corrida de minería y la siguiente (el mismo umbral de la alerta de HU02), 0 en caso contrario. Su justificación y sus limitaciones se analizan en la Sección~\ref{sec:variable-objetivo}.
	\item \textbf{Estrategia de etiquetado}: automática y retrospectiva, sin intervención manual. Cada par de scores consecutivos de un mismo producto genera un ejemplo, lo que es posible porque el sistema persiste el historial completo de scores y no solo el último.
	\item \textbf{Variables de entrada (\emph{features})}: los componentes del score conocidos en cada corrida y su variación respecto de la corrida anterior (Sección~\ref{sec:ml-reproducibilidad}).
	\item \textbf{Separación entrenamiento/validación}: corte temporal con purga y embargo, en lugar de una separación aleatoria, para que ninguna información posterior al corte influya en el entrenamiento (Sección~\ref{sec:control-fuga}).
	\item \textbf{Métricas de evaluación}: como la clase positiva es minoritaria, se priorizan la PR-AUC frente a la prevalencia, la matriz de confusión, la tasa de falsos positivos y el \emph{recall} de la clase positiva por sobre la exactitud: perder una tendencia real es más costoso para el vendedor que una señal de más (Sección~\ref{sec:ml-resultados}).
\end{itemize}

\section{Metodología de desarrollo}\label{sec:metodologia}

\subsection{Metodología}

El desarrollo del proyecto se llevó adelante bajo un enfoque ágil de tipo Kanban: ciclos cortos e incrementales de trabajo, integración continua hacia el entorno de producción y ciclos de feedback frecuentes con el tutor, en lugar de iteraciones de duración fija (\emph{sprints}) cerradas de antemano y definidas por adelantado. \textcite{BeckEtAl2001} definen los principios centrales de este tipo de metodologías (entrega temprana y continua de software funcionando, e incorporación del cambio incluso en etapas avanzadas del desarrollo), que se reflejan directamente en la forma de trabajo adoptada en este proyecto.

Esta elección se justifica por tres motivos concretos, verificables en el historial de control de versiones del proyecto:

\begin{itemize}
	\item \textbf{Incrementos pequeños y frecuentes}: 63 \emph{commits} entre el 21 de abril y el 31 de agosto de 2026 (aproximadamente cuatro meses y medio), cada uno acotado a un cambio puntual (una corrección, una funcionalidad o un ajuste de documentación) en lugar de entregas grandes y espaciadas.
	\item \textbf{Integración continua}: cada incremento se despliega automáticamente al entorno de producción en Render ante cada cambio en la rama principal (RNF03, Sección~\ref{sec:trazabilidad}), permitiendo validar el sistema en condiciones reales en vez de acumular trabajo sin probar.
	\item \textbf{Reorganización del trabajo en respuesta a feedback}: el plan de tareas se ajustó explícitamente en más de una ocasión a partir de devoluciones del tutor (documentadas tras la entrega del 25\,\% y nuevamente tras la del 50\,\%), incorporando esos cambios como parte del flujo normal de trabajo en lugar de tratarlos como una fase separada de corrección final.
\end{itemize}

Se descartó una metodología estructurada de tipo cascada porque el proyecto combina componentes con distinto grado de incertidumbre: el pipeline de captura y el dashboard tenían requerimientos claros desde el inicio, mientras que el diseño del score de tendencia y, más adelante, el del modelo de Machine Learning supervisado (Sección~\ref{sec:evolucion-tecnica}) se fueron ajustando a medida que se disponía de más datos reales, algo que un enfoque secuencial con etapas cerradas de antemano no habría permitido sin retrabajo significativo.

\subsection{Arquitectura y tecnologías utilizadas}

El diseño inicial contemplaba un desarrollo íntegramente en Python, con librerías de análisis de datos y machine learning (pandas, numpy, scikit-learn) y de visualización (matplotlib, seaborn), sobre una base de datos MySQL o una alternativa NoSQL. En el diseño técnico esas decisiones se revisaron: se optó por unificar el desarrollo en JavaScript/TypeScript sobre Next.js, exponiendo el sistema como una aplicación web con backend propio (API REST) en lugar de mantener un script de análisis separado del dashboard, y por usar PostgreSQL como motor relacional gestionado. El stack resultante es el que se detalla a continuación, con un ajuste adicional durante la implementación que se explica más abajo. Python se reserva para el motor analítico y de Machine Learning (ver el alcance definido en la Sección~\ref{sec:alcance}).

\subsubsection{Evolución de las decisiones técnicas}\label{sec:evolucion-tecnica}

Durante la implementación del prototipo, el stack preliminar fue ajustado: el backend y la captura de datos se desarrollaron finalmente sobre Next.js (API Routes) y Node.js, unificando frontend y backend en un único lenguaje (TypeScript) y un único despliegue, lo que reduce la complejidad operativa del proyecto. La capa de persistencia (PostgreSQL, gestionada mediante el ORM Prisma) y la arquitectura general de componentes (captura \(\rightarrow\) base histórica \(\rightarrow\) motor analítico \(\rightarrow\) API \(\rightarrow\) dashboard) se mantienen sin cambios: se modificó la herramienta de implementación, no el diseño. Python (Pandas + Scikit-Learn) se reserva para el motor analítico y de Machine Learning, integrado leyendo directamente la base histórica PostgreSQL.

\subsubsection{Arquitectura general}

La arquitectura del sistema se encuentra organizada en distintos componentes que trabajan de manera integrada para permitir la captura, procesamiento, almacenamiento y visualización de información relacionada con tendencias comerciales.

\paragraph{Diagrama de componentes}

\begin{figure}[H]
	\centering
	\includegraphics[width=0.95\textwidth]{./images/diagramas/diagrama_componentes.png}
	\caption{Diagrama de componentes del sistema en producción. Fuente: elaboración propia.}
	\label{fig:diagrama-componentes}
\end{figure}

El flujo de datos comienza con consultas periódicas a la API oficial de Mercado Libre. Luego, la información recolectada se almacena en una base histórica. A partir de ese histórico, el motor analítico calcula métricas temporales que permiten identificar productos con crecimiento sostenido o cambios relevantes. El backend expone esos resultados para que el dashboard los presente de manera visual.

El frontend (\emph{Dashboard (React)}, dentro del Carril 2 de la figura) cumple la función de representar la información de manera visual e intuitiva, permitiendo interpretar tendencias, métricas temporales y variaciones de comportamiento de los productos. La visualización de datos resulta fundamental para facilitar la toma de decisiones y transformar grandes volúmenes de información en indicadores comprensibles para el usuario.

Por otro lado, el backend (\emph{API REST (API Routes)}, también dentro del Carril 2) actúa como el componente encargado de administrar el procesamiento general de la plataforma. Su función principal consiste en organizar la información obtenida, coordinar los distintos procesos internos y garantizar el correcto funcionamiento de la lógica del sistema.

El motor de minería de datos (subsistema \emph{Captura automatizada, Carril 1}) representa uno de los elementos centrales del proyecto, ya que permite automatizar la obtención y análisis de información proveniente del marketplace. Su importancia radica en la capacidad de detectar patrones, registrar cambios temporales y construir históricos que luego pueden utilizarse para identificar comportamientos emergentes.

La persistencia de datos (\emph{Base Histórica} en la figura; el detalle de las tablas se muestra más adelante en el diagrama Entidad-Relación) cumple un rol clave dentro de la plataforma debido a que posibilita almacenar información histórica de manera organizada y continua. Mantener registros temporales permite realizar comparaciones, analizar evolución de tendencias y generar bases de información útiles para futuros modelos analíticos.

El monitoreo (\emph{probe\_endpoints.js}) es un script que se ejecuta a demanda, fuera de las corridas programadas: registra la disponibilidad y la latencia de los endpoints de la API en \texttt{EndpointHealthLog}, lo que permite detectar interrupciones o cambios que puedan afectar la recolección de información. El Carril 1 corre en GitHub Actions y encadena en cada corrida la minería, el cálculo del score, la predicción del índice ML, la generación de alertas con su notificación push y el respaldo de la base; el modelo se entrena fuera de la corrida y se versiona en el repositorio.

La arquitectura opera además en los dos carriles complementarios que se distinguen en la figura. El primero es el carril de captura en segundo plano: los procesos programados que construyen el histórico de manera sistemática y controlada, tres veces por día. El segundo es un carril de consulta en tiempo real: desde el dashboard, el usuario puede buscar productos puntuales consultando la API oficial en vivo, sin esperar a la próxima corrida de captura. Esta separación protege la recolección sistemática (cuyo ritmo está calibrado para respetar los límites de la API) de la carga variable de las consultas interactivas, y permite contrastar el histórico propio con el estado instantáneo del marketplace.

\subsection{Validación del sistema}\label{sec:pruebas}

Sobre el sistema en producción se aplicaron dos técnicas de prueba distintas: pruebas de rendimiento sobre los requerimientos no funcionales, y una prueba de usabilidad embebida en una entrevista con un usuario real. La cobertura de pruebas automatizadas (unitarias y de integración) se documenta en la Sección~\ref{sec:cobertura-tests}.

\subsubsection*{Pruebas de rendimiento (RNF02)}

La medición del 10/08/2026 (Tabla~\ref{tab:evidencia}) mostró que \texttt{/api/trend-scores} respondía en 6,3--7,6\,s, por encima del objetivo de 3\,s de RNF02. La causa identificada fue que la consulta traía el historial completo de \texttt{TrendScore} (más de 7700 filas a esa fecha) con el historial de precios de cada producto anidado, cuando el dashboard solo necesita las últimas 2 mediciones por producto para calcular la variación mostrada en pantalla. La corrección, aplicada acotando la consulta a esas últimas 2 mediciones, se verificó en producción el 21/09/2026 con 5 muestras: el tiempo de respuesta bajó a 1,7--2,9\,s en caliente, dentro del objetivo. La medición se repitió el 09/10/2026, con alrededor de un 20\,\% más de scores acumulados: \texttt{/api/trend-scores} respondió en 2,0--2,8\,s, \texttt{/api/insights} en 1,0--2,0\,s y \texttt{/dashboard} en 0,5--0,9\,s. El objetivo se sigue cumpliendo, pero el margen de \texttt{/api/trend-scores} es el más ajustado: su consulta recorre todos los scores para quedarse con los dos últimos de cada producto, y su costo crece con el histórico.

\subsubsection*{Prueba de usabilidad}

La Entrevista 2 (Anexo~\ref{anexo:entrevista2}, Sección~\ref{chapter06}) incluyó una instancia de prueba de usabilidad: se mostró el dashboard en funcionamiento a un vendedor real (Lucas) y se le pidió que interpretara la pantalla sin explicación previa (pregunta 3, ``¿Qué entendés que muestra esta pantalla?''). El entrevistado identificó correctamente el propósito del ranking y del score sin asistencia, lo que valida que la interfaz comunica su función principal sin necesidad de instrucciones adicionales.

Esa misma instancia motivó una decisión de diseño a partir de sus resultados: la pregunta sobre qué le faltaba a la herramienta (pregunta 8) y la objeción de que el score funcionaba como una ``caja negra'' (pregunta 10) llevaron a que el desglose de sus componentes se muestre explícitamente en el dashboard en lugar de solo el puntaje final (cuatro en la versión mostrada en esa entrevista: frecuencia, permanencia, ranking y estabilidad; cinco desde la incorporación de la saturación), decisión ya documentada en la Sección~\ref{sec:score-formal}.

\subsubsection{Cobertura de pruebas automatizadas}\label{sec:cobertura-tests}

Además de las pruebas de rendimiento y usabilidad anteriores, se construyó una suite de pruebas unitarias automatizadas (Vitest) sobre el núcleo de lógica de negocio del sistema: el cálculo del score de tendencia (\texttt{computeComponents}, Sección~\ref{sec:score-formal}), la validación de datos de entrada (email y contraseña de registro) y el manejo de sesiones (creación, verificación y expiración de JWT). A esa suite se sumaron luego las reglas del tablero de oportunidades (clasificación de señales, frescura de los productos, tendencia de vendedores y niveles del índice ML), incluido un test que verifica que la aplicación use los mismos cortes del índice que el modelo entrenado (Sección~\ref{sec:ml-calibracion}). Con la incorporación de las notificaciones push se agregaron también la validación de las suscripciones que envían los navegadores y el armado de los avisos. La suite ejecuta 76 pruebas, todas exitosas, con una cobertura de 97,4\,\% de sentencias, 97,9\,\% de ramas y 96,2\,\% de funciones sobre ese núcleo, por encima del umbral de 85\,\% exigido.

El alcance de la cobertura se define deliberadamente sobre la lógica de negocio pura (funciones que transforman datos de entrada en una salida verificable), no sobre la orquestación de I/O (consultas a PostgreSQL vía Prisma, llamadas a la API externa de Mercado Libre). Mockear por completo esas dependencias para elevar artificialmente el porcentaje de cobertura no agregaría una prueba real: validaría que el mock se comporta como se lo programó, no que el sistema funciona contra una base de datos o una API real. Esa validación ya se cubre, de forma más representativa, con las pruebas de rendimiento y usabilidad sobre el sistema en producción (más arriba en esta misma sección) y con la evidencia cuantitativa de la Sección~\ref{sec:evidencia-cuantitativa}.

Entre los casos cubiertos por la suite se incluye una regresión explícita del bug de validación de email corregido (Sección~\ref{sec:viabilidad-legal}): un caso de prueba verifica específicamente que `\texttt{a@}' sea rechazado, el caso que antes pasaba la validación de forma incorrecta.

\section{Viabilidad legal y técnica}\label{sec:viabilidad-legal}

El proyecto no aborda una temática sensible en términos legales (no procesa datos de salud, alimentación ni pone en riesgo la vida de los usuarios): los datos de producto (precios, categorías, publicaciones) provienen exclusivamente de la API oficial de Mercado Libre (Sección~\ref{sec:tecnologias-utilizadas}) y son públicos, sin acceder a información privada de compradores o vendedores de Mercado Libre (Sección~\ref{sec:alcance}). Por ese motivo, no corresponde incluir un descargo de responsabilidad legal específico más allá del cumplimiento de los términos de uso de la API oficial, ya documentado como RNF05 (gestión segura de credenciales OAuth2 exclusivamente del lado servidor, Sección~\ref{sec:trazabilidad}).

Con la incorporación de cuentas de usuario (RF08, Sección~\ref{sec:modelo-negocio}) el sistema sí pasó a recolectar un dato personal propio, no de Mercado Libre: el email de quien se registra. El tratamiento se mantiene acotado a lo estrictamente necesario para el modelo freemium: solo email y contraseña hasheada (RNF07), sin datos de pago, dirección ni información adicional, en línea con los principios de minimización de datos de la Ley 25.326 de Protección de Datos Personales. La suscripción del modelo freemium reutiliza ese mismo email de cuenta. Las notificaciones push de las alertas (RF09, HU02) agregan un único dato técnico: la suscripción del navegador (la dirección que asigna el servicio de push y dos claves de cifrado). Solo se guarda cuando el cliente activa las notificaciones de forma explícita y acepta el permiso del navegador, se asocia a su cuenta, no identifica a la persona, no se usa para ningún otro fin y se elimina cuando el cliente las desactiva o cuando el servicio de push la declara vencida. Queda como trabajo pendiente para una eventual operación comercial real redactar una política de privacidad formal.

Los datos personales recolectados durante el User Research (Sección~\ref{chapter06}) se tratan bajo el mismo principio de minimización. La encuesta fue anónima y voluntaria, y sus resultados se reportan exclusivamente en forma agregada (porcentajes y conteos), sin exponer respuestas individuales identificables. Las tres entrevistas en profundidad se registraron con consentimiento informado de cada participante, y los nombres utilizados en su transcripción (Anexos~\ref{anexo:entrevista1} a~\ref{anexo:entrevista3}) son pseudónimos elegidos para preservar el anonimato: no se registran apellidos, datos de contacto ni otra información identificatoria de los entrevistados.

En cuanto a viabilidad técnica, el proyecto es enteramente de software: no requiere fabricación ni adquisición de hardware específico, dado que se ejecuta sobre infraestructura \emph{cloud} gestionada (Render para el backend y Supabase para la base de datos PostgreSQL), ambas con planes ya operativos y verificados en producción (Sección~\ref{sec:evidencia-cuantitativa}). Por lo tanto, este criterio también se da por cumplido sin requerir un análisis adicional de producción o compra de equipamiento.
